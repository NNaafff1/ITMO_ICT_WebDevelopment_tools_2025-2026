    Выводы¶

    Что было сделано¶

    Подзадача из ТЗ Реализация
    1. Упаковать FastAPI, БД и парсер в Docker Три Dockerfile-а + общий docker-compose с пятью сервисами
    2. Вызов парсера по HTTP из основного API POST /parser/parse синхронно дёргает parser:8001/parse
    3. Вызов парсера через очередь Celery + Redis, POST /parser/parse-async + GET /parser/tasks/{id}

    Чему научились¶

    Docker и оркестрация. Каждый сервис в своём контейнере, общая сеть внутри compose, имена сервисов работают как DNS. Healthcheck-и для db и redis решают классическую проблему «api стартанул раньше БД». Volume для PostgreSQL переживает рестарты.

    Микросервисная архитектура. Парсер вынесен в отдельный сервис не ради моды, а потому что у него своя нагрузка и свои отказы. Воркер вынесен ещё дальше, чтобы можно было масштабировать только тяжёлую часть. Все три части (api, parser, worker) общаются по HTTP или через очередь — никаких прямых импортов между ними.

    Очереди задач. Celery + Redis — стандартный стек для фоновых задач в Python-мире. send_task по имени позволяет API не зависеть от кода воркера. Ретраи на сетевые ошибки повышают надёжность. Опрос статуса через AsyncResult — простой и понятный паттерн.

    Что бы улучшил¶

    1. WebSocket-уведомления вместо опроса. Когда задача завершается, клиент мог бы получить пуш, а не опрашивать GET /tasks/{id} каждые пару секунд.
    2. Flower — веб-UI для мониторинга Celery-задач. Один дополнительный контейнер, и видно очередь, активные задачи, статистику воркеров.
    3. Periodic tasks (Celery beat). Регулярно перепарсивать фиксированный список URL — например, чтобы держать актуальные описания популярных языков. Это упомянуто как опциональная часть ТЗ для тех, кто хочет глубже разобраться с Celery.
    4. Multi-stage Docker builds. Сейчас образы ~150–200 МБ. Multi-stage сборка с отдельным builder-стадией могла бы убрать ~50 МБ инструментов компиляции из финального образа.
    5. Alembic-миграции в init-контейнере. Сейчас таблицы создаются через Base.metadata.create_all в lifespan-event. Это не покрывает изменения схемы. В реальном проекте надо запускать alembic upgrade head в отдельном init-контейнере перед стартом api.

    Финальная картинка¶

                Один docker compose up — пять сервисов в воздухе:

   ┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐
   │   api    │  │  parser  │  │  worker  │  │    db    │  │  redis   │
   │ :8000    │  │  :8001   │  │  Celery  │  │ Postgres │  │ broker + │
   │ FastAPI  │  │ FastAPI  │  │          │  │   :5432  │  │  backend │
   │ + JWT    │  │ + bs4    │  │          │  │          │  │   :6379  │
   └──────────┘  └──────────┘  └──────────┘  └──────────┘  └──────────┘

      sync и async парсинг работают «из коробки»,
      воркеры можно масштабировать на лету: docker compose up --scale worker=4
