    Архитектура¶

    Пять сервисов¶

    Система разбита на пять сервисов, каждый — в своём Docker-контейнере.

                          ┌─────────────┐
                      │   Клиент    │
                      │  (curl/UI)  │
                      └──────┬──────┘
                             │ HTTP :8000
                             ▼
       ┌──────────────────────────────────┐
       │            api (FastAPI)         │
       │   /auth /users /projects ...     │
       │   /parser/parse                  │──┐
       │   /parser/parse-async            │  │ HTTP
       │   /parser/tasks/{id}             │  │  :8001
       └──────┬───────────┬───────┬───────┘  │
              │           │       │          │
       SQL    │           │ Celery│          ▼
       :5432  │           │ send  │   ┌──────────────────┐
              │           │ :6379 │   │ parser (FastAPI) │
              ▼           ▼       │   │   POST /parse    │
       ┌────────────┐ ┌──────┐    │   │ requests + bs4   │
       │ db (PG 15) │ │redis │    │   └─────────┬────────┘
       │ teamfinder │ │ 7    │    │             │ HTTP
       └─────▲──────┘ └──┬───┘    │             │ scraping
             │ SQL       │ poll   │             ▼
             │           │        │      Wikipedia.org
             │     ┌─────▼────────▼────┐
             └─────┤  worker (Celery)  │
                   │  parse_url_task   │
                   └───────────────────┘

    Кто с кем разговаривает¶

    Источник Назначение Протокол Зачем
    Клиент api HTTP :8000 Все пользовательские запросы
    api db PostgreSQL :5432 Чтение/запись бизнес-данных
    api parser HTTP :8001 Синхронный вызов парсинга
    api redis redis :6379 Постановка задач в очередь и опрос статуса
    worker redis redis :6379 Получение задач из очереди
    worker parser HTTP :8001 Тот же сервис-парсер, что и для sync — один источник истины
    worker db PostgreSQL :5432 Сохранение результата парсинга в таблицу skills
    parser Wikipedia HTTPS Скачивание HTML страниц

    Почему именно так разнесено¶

    Парсер вынесен в отдельный сервис. Этого прямо требует ТЗ («отправлять запрос парсеру, запущенному в отдельном контейнере»), но у такого деления есть и техническое обоснование: парсинг и обслуживание клиентов — разные характеры нагрузки. Парсер может тормозить из-за медленного ответа Wikipedia, и эта медлительность не должна замедлять основное API.

    Воркер вынесен в третий контейнер. Это позволяет горизонтально масштабировать только тяжёлую часть: при росте нагрузки запускается несколько реплик worker — docker compose up --scale worker=4, и очередь сама распределит между ними задачи.

    Воркер ходит к парсеру по HTTP, не импортирует код напрямую. Альтернативой было бы скопировать parser.py в воркер. Это создало бы две точки изменения логики парсинга. Лучше иметь один сервис — если завтра парсер переедет на другую библиотеку или начнёт ходить через прокси, ни API, ни воркер не заметят.

    Воркер пишет в БД напрямую, минуя API. Альтернатива — вызывать HTTP-эндпоинт API из воркера — создала бы циркулярную зависимость и лишний хоп. Прямой доступ воркера к БД нормален: это backend-сервис, а не пользовательский клиент. Схема дублирована в worker/models.py, чтобы воркер не зависел от кода api/.

    Поток данных¶

    Синхронный парсинг¶

    Клиент → POST /parser/parse {url}
   → api: HTTP POST parser:8001/parse {url}
       → parser: GET wikipedia
       → parser: парсит HTML → (name, description)
   ← api получает (name, description)
   → api: UPSERT в skills (db)
   ← api: 201 + SkillResponse

    Асинхронный парсинг¶

    Клиент → POST /parser/parse-async {url}
   → api: celery.send_task("parse_url_task", [url])
       → задача попадает в очередь Redis
   ← api: 202 {task_id}

(параллельно)
worker слушает Redis
   → worker забирает задачу
   → worker: HTTP POST parser:8001/parse
   → worker: UPSERT в skills
   → worker: записывает result в Redis

Клиент → GET /parser/tasks/{task_id}
   ← api: {status: "SUCCESS", result: {...}}
